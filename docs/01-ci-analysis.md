## 1. Research: что известно и чего нет

**Источник:** фрагмент лога CodeBuild запуска от 2026-10-28 (ветка `dev`): вывод `npm run cy:tests` (`npx cypress run`) и фаза `POST_BUILD`.

**Чего в логе нет** (поэтому по ним выводов не делаю):

- содержимого 20 скриншотов падений (они сохранены в `cypress/screenshots/`, в лог не попали).

**Окружение прогона:** Cypress 14.4.0, Electron 130 (headless), Node v22.x, 14 спеков `cypress/e2e/**/*.feature`.

**Падение.** В `erpTaskApprove.feature` 10 тестов упали одинаково:

> `CypressError: Timed out retrying after 10000ms: The command was expected to run against origin <APP_HOST> but the application is at origin <SSO_HOST>.`

То есть в момент проверки браузер находится не на портале, а на домене SSO (логин). Это не ошибка ассертов: приложение «ушло» со страницы (по скриншоту, который открыл автор теста, это страница с ошибкой 403).

**Все 10 упали в обеих попытках** (`Attempt 1 of 2` и `attempt 2`, 20 скриншотов), значит это не разовый сбой.

**Порядок результатов в спеке** (по порядку в логе):
`1 ✓` → `2–9 ✗` (8 подряд) → `10–12 ✓` → `13–14 ✗`.

**Что это значит для CI:**
- `npm run test || TEST_FAILED=true` перехватывает ошибку, затем генерируется Allure-отчёт, старый отчёт в `<BUCKET>` удаляется, новый загружается, после этого `exit 1`. Фаза `POST_BUILD` помечена `FAILED` намеренно: **красная сборка вызвана падением тестов, а не поломкой самого пайплайна** (Allure и S3 отработали).
- Шум `tput: No value for $TERM` безвреден.

## 4. Implement: разбор стадии `post_build`

Построчно, по `buildspec.yml`:
1. `export INTEGRATION_ENDPOINT=$(terraform output remote_url)`: адрес развёрнутого стенда ветки, против которого идут UI-тесты. Если стенд недоступен, тесты упадут все, а не 10.
2. `MOCK_KEY`, `ALLURE_BUCKET_NAME`: параметры стенда и бакет отчётов.
3. `npm run cy:verify`, `cy:info`: проверка и информация о бинарнике Cypress.
4. `npm run test || TEST_FAILED=true`: тесты не прерывают фазу, ошибка запоминается.
5. Если `TEST_FAILED`: генерируется Allure-отчёт (`--single-file`, ~13.5 МиБ), **старый отчёт ветки удаляется** (`s3 rm`), загружается новый, `exit 1`.
6. Если тесты зелёные, отчёт **не** генерируется и не загружается.

**Если стадия падает:** `POST_BUILD: FAILED`, артефакты выгружаются (стадия `UPLOAD_ARTIFACTS` в логе прошла), сборка красная, деплой остаётся (terraform уже применён).

## 6. Verify: как найти запрос без мока

**Что уже проверено по коду** (UI-тесты полностью замоканы, любой незамоканный запрос уходит на реальный бэкенд):
- страница ERP при загрузке запрашивает: `GET tasks/{id}/erps`, `GET sites/{id}/registrations`, типы продуктов и программ (`types/product`, `types/program`), права (`.../permissions`), чек-лист (`GET checklists/{id}`);
- при действиях: `PUT tasks/{id}/erps` (сохранение/approve) и `PUT tasks/{id}` (обновление статуса задачи);
- в `erpTaskApprove.ts` замоканы: `GET **/tasks/{id}/erps*`, `PUT **/tasks/*/erps*`, `GET **/sites/**/registrations*`, `GET **/checklists/{id}*`, `PUT /tasks/{id}`, `GET **/permissions`; типы мокаются глобально в `support/commands.ts`.
- Любой другой запрос страницы, не входящий в этот список, является кандидатом.

**Как найти его (локальный запуск):**
1. Запустить падающий спек локально в интерактивном режиме (`cypress open`, спек `erpTaskApprove.feature`) на сценарии «Display Approve All dialog».
2. В панели Cypress (Command Log) запросы без мока показываются как обычные `(xhr)` / `(fetch)` без пометки `(stubbed)`. Открыть DevTools → Network, отфильтровать по `api/v1` и найти запрос со статусом 403 (или 401).
3. Записать метод и URL этого запроса и сверить с `client/src/app/services/*.ts`: какой сервис и какое действие его вызывает.
4. Понять, почему проходят 4 сценария: сравнить их Given-шаги с падающими (какого запроса не происходит в проходящих).
5. Добавить мок (`cy.intercept` с алиасом) в общий Given/хелпер, а не копировать в каждый сценарий, и прогнать весь спек повторно.
6. Сверить с историей спека: изменились ли `erpTaskApprove.ts` или код приложения (задача SOLO-4939) перед этим запуском; возможно, приложение недавно добавило новый запрос (`git log` по `erp-task` показывает правки, например «add pending approval support»).

## 7. Описание инцидента для тикета (черновик)

**Заголовок:** CI (ветка `dev`): 10 из 14 тестов `erpTaskApprove.feature` падают с редиректом на SSO.

**Что произошло:** в запуске CodeBuild от 2026-10-28 Cypress-спек `erpTaskApprove.feature` завершился с 10 падениями из 14 (оба ретрая). Ошибка: `The command was expected to run against origin <APP_HOST> but the application is at origin <SSO_HOST>`. Всего в запуске 126 из 145 тестов прошли: 12 спеков зелёные, 9 сценариев `createContact.feature` в статусе pending.

**Затронуто:** `erpTaskApprove.feature` (10 тестов), сборка помечена как FAILED на `POST_BUILD`. Пайплайн отработал штатно: Allure-отчёт сформирован и загружен.

**Причина:** в падающих сценариях страница ERP отправляет запрос к `/onboardings`, для которого в тесте нет `cy.intercept`. Реальный бэкенд стенда отвечает 403, `error.interceptor.ts` уводит страницу на Forbidden, и следующая команда Cypress падает по смене origin. Категория: тест (недостающий мок), не дефект приложения и не окружение. Найдено локальным прогоном (Network).

**Исправление:** добавлен `cy.intercept` на `/onboardings` в спеке `erpTaskApprove`; повторный прогон спека зелёный. Таймауты и ретраи не менялись.

**Дополнительно:** тест «Save with Apply to all copies…» в `erpTaskSaveAndSubmit.feature` прошёл только со 2-й попытки. Это кандидат во flaky, данные по нему собираются отдельно (см. `cert/daily-comms`, раздел 3.5).

**Статус:** решено. **Последующие шаги (отдельные задачи):** улучшения 1–3 из раздела 5, в первую очередь страховочный перехватчик незамоканных запросов.
